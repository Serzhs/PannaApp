# 0003: Sign in with Google and Apple

**Status:** In progress
**Depends on:** 0001, 0002

## Context

0001 created the `users`, `identities` and `refresh_tokens` tables and wrote nothing to them. 0002 built the components a screen needs. Every recipe belongs to an author, so nothing else can be built until a user can have an account.

The app has no passwords. Identity comes from Google or Apple, which removes password storage, brute forcing, breached passwords, reset flows and the "is this email taken" leak in one decision. What it adds is a hard dependency on two outside services and a real setup cost before anyone can sign in.

## Goal

A user signs in with Google or Apple in one tap, and stays signed in after restarting the app.

## Out of scope

- Passwords of any kind. There is a development-only sign-in, described in its own section below, and it is deliberately not a password: it mints a session for a user that is already in the seed, and it cannot create one.
- Facebook, and any third provider. Google and Apple cover almost everyone, and adding another later is a small change.
- Linking or unlinking providers from a settings screen. Automatic linking is described below; doing it by hand is a later spec.
- Account deletion, profile editing, avatars.
- Choosing a language or unit system. 0006 owns that; this spec follows the device locale.
- Any recipe screen. The signed-in destination is a placeholder.

## Prerequisites

These are not code, and nothing works without them. They are listed because "clone and run" is no longer the whole story.

- A Google Cloud project with OAuth client ids for iOS and Android. The iOS one is for bundle id `app.panna.mobile`.
- An Apple Developer account, which is paid, with Sign in with Apple configured for the app id. A free Apple ID cannot turn the capability on, and that holds in the simulator too.
- Both sets of client ids in `.env`, validated at boot by 0001's environment schema. `GOOGLE_CLIENT_ID_IOS` is read by the API as the audience it accepts _and_ by the app's build config as the client id it asks Google with, so the two cannot disagree. `APPLE_CLIENT_ID` is the bundle id.
- **An Xcode build of the app, not Expo Go.** Neither provider works inside Expo Go: Apple's token would name Expo Go's bundle id, and Google's redirect needs a URL scheme only our own build registers. The client id is baked into that build, so changing it means building again.
- None of the above is needed to run the app locally: the development sign-in below covers that, and it is the only reason this spec is buildable before the accounts exist.
- A network connection. Sign-in cannot work offline, for developers or for tests, which is a real change from a local-only project.

## Data model

No new tables. `users`, `identities` and `refresh_tokens` exist from 0001.

**Account linking.** A sign-in is matched to an existing user by `(provider, subject)` first, which is the only stable key. If there is no match and the provider says the email is verified, the identity is attached to the user holding that email, or a new user is created with it. If there is no match and no verified email, the sign-in is refused with `AUTH_PROVIDER_TOKEN_INVALID`.

Linking on an _unverified_ email would be account takeover: anyone who can get a provider to assert an address they do not own would inherit the account behind it. Creating a separate account instead is not possible either, because `users.email` is unique and the address may already be taken. Google and Apple both verify addresses, so in practice this path is not reached; it exists so that it fails closed if it ever is.

**A name may be blank.** Google puts one in its token. Apple hands one over only if the person agrees, and only the first time. When neither supplies one, `displayName` is stored empty, until 0017 makes it editable.

**Apple's private relay.** Apple lets people hide their real address, giving a unique relay address per app instead. It will never match an existing user, so someone who signs in with Apple privately and later with Google gets two accounts, and there is no way for the app to know they are the same person. That is a limitation of the choice, not a bug to fix here.

**Apple sends a name once.** The display name arrives only on the very first authorisation, from the client rather than from the token, and never again. If it is not captured then it is gone, so the first sign-in stores it and later ones leave it alone.

## Development sign-in

Real sign-in needs provider accounts and an Xcode build of the app, and Expo Go can use neither
provider. Without this, nobody can get past the first screen in Expo Go, or before the accounts
exist.

**`POST /api/auth/dev-session`**
Body: `{ email }`
200: the same body as `POST /api/auth/session`, so the client takes one code path and the real one
gets the exercise.
404 if no user has that email. It matches a user that the seed already created and **cannot create
one**, so it mints a session for accounts that exist rather than for anything a caller names.

**Three independent gates, because one is how these things ship.**

1. **The server does not register the route** unless `NODE_ENV` is not `production` _and_
   `ALLOW_DEV_SIGN_IN` is `true`. This is module registration, not an `if` inside a handler: when it
   is off the controller is never loaded, so there is no code path to reach, only a 404.
2. **The API refuses to boot** when `ALLOW_DEV_SIGN_IN` is `true` and `NODE_ENV` is `production`,
   with a message naming the variable. A misconfigured production API does not start rather than
   starting with a door open, which is the behaviour 0001 already established for a bad environment.
3. **The client's button is compiled out.** The affordance sits behind `__DEV__` in a module-level
   ternary, the pattern 0002 proved gets dead-code eliminated, so the string does not appear in a
   release bundle at all. A criterion below checks that by grepping an export.

The honest accounting: this is still a sign-in path that must never reach production, which is what
the original scope note warned about. What makes it acceptable is that failing safe is the default at
all three layers, that it can only reach seeded accounts, and that each gate is checked by a test
rather than by intention. It comes out the moment real sign-in works locally.

## API contract

Through the contract in `packages/shared`. Error codes this spec introduces, alongside `VALIDATION_FAILED` and `RATE_LIMITED` from 0001:

`AUTH_PROVIDER_TOKEN_INVALID`, `AUTH_TOKEN_INVALID`, `AUTH_TOKEN_EXPIRED`, `AUTH_TOKEN_REVOKED`.

There is no code for "this email already exists", because there is no path where a user asserts an email.

**POST /api/auth/session**
Body: `{ provider: 'google' | 'apple', idToken, nonce, displayName? }`
200: `{ user: { id, email, displayName }, accessToken, refreshToken }`, for both a new account and an existing one. The response does not say which, because the client does not need to know and the difference is not the client's to act on.
401 with `AUTH_PROVIDER_TOKEN_INVALID` if the token fails any check.
429 when throttled per IP.

Verification, in full, per the Security section of `CLAUDE.md`: signature against the provider's published keys, issuer, audience matching our own client id, expiry, issued-at, and `nonce` matching the value the client generated for this attempt. `email` is used only when the provider marks it verified. An access token is never accepted in place of an ID token.

`displayName` is accepted only when creating a user, is treated as untrusted text, and is ignored on every later sign-in.

**POST /api/auth/refresh**
Body: `{ refreshToken }`
200: `{ accessToken, refreshToken }`. The old token is revoked and a new one issued on every use.
401 with `AUTH_TOKEN_INVALID`, `AUTH_TOKEN_EXPIRED` or `AUTH_TOKEN_REVOKED`.

**Reuse is treated as theft.** Presenting a token that has already been used revokes every token in that chain, not only the one presented, and logs it. A stolen refresh token therefore works once, after which both parties are signed out and there is a log line saying so. Revoking only the presented token would leave the thief's fresh token working while the victim's rotation failed, which is the wrong way round. Each refresh token records the token it replaced, so the chain is identifiable.

**POST /api/auth/logout**
Auth required. Revokes the caller's refresh token chain. 204.

**GET /api/me**
Auth required. 200: `{ id, email, displayName }`. 401 without a valid access token.

Refresh tokens are 256 bits of randomness stored as a SHA-256 hash, never written raw to the database or to logs. Failed verifications, throttle rejections and refresh reuse are logged as authentication events.

## UI

Expo Router with two route groups, `(auth)` and `(app)`. Built from 0002's components.

**`(auth)/index`**: the app name, a short line saying what it is for, and two buttons - Continue with Google, Continue with Apple. Nothing else. No email field, no password, no third option.

In a development build only, a third affordance appears under those two, taking the seeded developer account straight in. It is compiled out of a release bundle, per the Development sign-in section, and is styled as an ordinary `Button` so nobody mistakes it for a provider.

The two buttons follow Google's and Apple's own branding rules rather than the app's `Button` styling, per the Platform behaviour section of `CLAUDE.md`. Both providers require it, and it is the one place the design system does not win.

Sign in with Apple appears first on iOS, per Apple's guidance. **On Android only Google is offered** - the Apple web flow is poor enough not to ship, per the decision recorded under Open questions.

The client generates a fresh `nonce` per attempt. It gives the provider the SHA-256 of it and sends the API the nonce itself; the API hashes what it receives and compares it with the token's claim. The token therefore carries only the hash, so holding a captured token is not enough to present it.

Google runs through its browser sign-in sheet rather than its native SDK, because the free native library cannot pass a nonce. An iOS client has no secret, so the code is exchanged with PKCE alone.

States: idle, in flight with the pressed button showing a loading state and both disabled, and failed. A cancelled sign-in returns silently to idle, because cancelling is a choice rather than an error. A genuine failure shows a message and lets the user try again or use the other provider. Being offline says so plainly, since sign-in is the one thing that cannot work without a connection.

**`(app)/index`**: placeholder home screen showing the display name and a sign-out button. Replaces 0001's placeholder. Recipes come in 0005.

The root layout chooses the group based on whether a session exists, showing a splash state while it checks rather than flashing the sign-in screen.

Tokens are stored in `expo-secure-store`. The shared client attaches the access token, and on a 401 attempts one refresh, retries once, and on failure clears the session and returns to sign-in. Concurrent 401s trigger exactly one refresh call.

## Open questions

**Sign in with Apple is built but unverified.** Google sign-in has been exercised end to end on a real
build against a real account. Apple has not: the button, the nonce, the token verifier and the
name-once rule are all written, but they cannot be tried until a paid Apple Developer account exists
and the Sign in with Apple capability is enabled for `app.panna.mobile`. The provider-level acceptance
criteria above therefore stand as checked for Google only, and the Apple button on a device today
returns an error. This is picked up when the account exists, before this spec is closed.

**Two accounts, one person: accepted.** Apple's private relay guarantees that someone who signs in with
Apple privately and later with Google gets two accounts, and nothing can connect them. That is a
limitation of choosing providers over passwords, not a bug to fix here. Most people use one provider
and never meet it. Manual linking from settings is possible later, but merging two accounts of recipes
is its own spec and is not worth pre-empting.

**Sign in with Apple is not offered on Android.** The Android path is a web flow rather than the native
sheet, and it is poor enough not to ship. The consequence is real and should not be glossed: **anyone
who signed up with Apple and later moves to Android cannot reach their recipes.** They would have to
start again. That is accepted for the MVP because the overlap of Apple sign-up and an Android switch is
small, but it is the kind of thing that becomes a support problem rather than a bug report, so it is
written here rather than discovered later.
