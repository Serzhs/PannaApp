# 0006: Internationalisation

**Status:** Approved
**Depends on:** 0003, 0005

**Changed by 0020:** the temperature half of the converter is gone with the column it served; mass and volume stay.

## Context

0003 ships English strings written directly into the sign-in screen, and 0005 adds many more. Every one of those literals is a string somebody will have to find and extract later, and the ones that get missed are found by users rather than by developers. The plumbing is cheap now and grows more expensive with every screen added.

## Goal

A user can run the app in English or Latvian, with correct plurals, locale-appropriate formats, and measurements in the system they think in.

## Out of scope

- Any third language. Adding one must cost a translation file and a line in the locale list, and this spec ships two.
- Translating recipe content. Titles, ingredient names and step bodies stay in the language their author wrote them in, always. The recipe does not record which language that is, because nothing would read it.
- Shipping a right-to-left language. The layout discipline that makes one possible is in scope; an actual RTL locale is not.
- Translation management tooling, string extraction pipelines, or a translator-facing service. Files are edited by hand in the repo.
- Converting volume to mass. See the limitation below.
- Localised recipe search or collation. Nothing searches yet.

## Data model

No new tables. Two columns created empty by 0001 come into use here:

- `users.locale` — a BCP-47 tag, or null for "follow the device".
- `users.unitSystem` — `metric` or `imperial`, or null for "derive from the locale".

Null is a real value in the first two and is not the same as the resolved value. A user on a `lv-LV` device who explicitly picks English has `locale = 'en'`; a user who never opened settings has `locale = null` and follows the device wherever it goes. Storing the resolved value on first launch would silently freeze a preference the user never expressed.

**Resolution order: explicit choice, then device, then English.** Null is not English. A Latvian on a Latvian phone who never opened settings gets Latvian; English is the last resort for a device asking for a language the app does not ship. `unitSystem` resolves the same way and ends at metric.

## API contract

**PATCH /api/me**
Auth required. Body: any subset of `{ locale, unitSystem, displayName }`. Either of the first two may be `null`, which restores "follow the device".
200: `{ id, email, displayName, locale, unitSystem }`.
400 with `VALIDATION_FAILED` if `locale` is not in the shipped set or `unitSystem` is not one of the two enum values.

**GET /api/me** gains `locale` and `unitSystem` in its response.

No other endpoint changes. The server does not translate anything, does not read `Accept-Language`, and does not convert units. It stores the preference; the client does the work.

## Translation

Files live at `apps/mobile/src/i18n/<locale>/<namespace>.json`, one namespace per feature, matching the `src/features/*` folders.

- Keys are structural, not English: `recipes.list.empty.title`, never `noRecipesYet`. A key derived from the English wording has to change when the English changes, which breaks every other language for no reason.
- English is the source. A key missing from another locale falls back to English rather than rendering the key, because a user seeing `recipes.list.empty.title` is a worse failure than a user seeing English. An empty string counts as missing too, so a key can be added to English first and the app stays usable until it is translated.
- Plurals use i18next's plural categories. Latvian resolves to `zero`, `one` and `other`, and its zero form applies to 0, 10, 20 and every number ending in zero, which no hand-written condition gets right by accident.
- Interpolated values are formatted through `Intl`, not concatenated.

## Units

Conversion happens on display only. Values are stored exactly as the author entered them, in the unit they chose, and `unitSystem` decides what the reader sees. Storing a canonical value instead would mean the author's own recipe reads back in numbers they did not write.

Conversion is within a dimension only:

- Mass to mass, `g`/`kg` to `oz`/`lb`.
- Volume to volume, `ml`/`l` to `tsp`/`tbsp`/`cup`/`floz`.
- `temperatureCelsius` to Fahrenheit.
- Count units - `piece`, `pinch`, `clove`, `slice` - are translated, never converted.

**Volume to mass is never attempted.** Turning `1 cup` of an ingredient into grams needs that ingredient's density: a cup of flour and a cup of honey differ by more than a factor of two. Guessing produces a recipe that is confidently, invisibly wrong, which is worse for a cooking app than showing a unit the reader has to think about. So an imperial reader sees cups for a volume and ounces for a mass, and never a mass derived from a volume.

Converted values are rounded to something a person would say - `250 ml` becomes `1 cup`, not `1.0567 cups` - and a converted value is marked as approximate in the UI so nobody weighs to a precision the conversion does not have. Volumes round to the nearest common cup or spoon fraction when one is close enough, and fall back to fluid ounces when none is, per the decision below.

**Ingredients and steps do not exist on any screen until 0007 and 0008.** This spec ships the conversion as a tested module in `src/features/units`, with the setting that drives it, and those specs put it on screen. The unit criteria below are therefore asserted against the module, not a screen.

A temperature written into a step's `body` as prose is not converted, because that would mean rewriting user text. Only `temperatureCelsius` converts, which is the reason the column exists.

## UI

**`(app)/settings`**, a new screen: language picker (Device, English, Latviešu), unit system picker (Device, Metric, Imperial), and the logout button, which moves here from the recipe list header. Each picker's "Device" option is the null state and shows what the device currently resolves to, so the choice is legible rather than blank.

Changing either takes effect immediately across the app, with no restart and no reload of the navigation stack.

**Every screen from 0003 and 0005** is swept for string literals. This spec is not done while one remains.

## Acceptance criteria

- [x] `pnpm typecheck`, `pnpm lint` and `pnpm test` pass across all three workspaces.
- [x] A lint rule fails the build on a user-visible string literal in a component, so the sweep cannot silently regress as new screens are added. _(`i18next/no-literal-string` over JSX text and the props that carry words, in every component and route; tests and the development gallery are exempt.)_
- [x] Switching to Latviešu changes every string on every screen built so far, with no English left except recipe content the user authored. _(Verified on an iPhone 17 Pro simulator: the change applies at once, with no restart. The Latvian wording is a draft for the owner to correct, per Decided.)_
- [x] A key present in English and missing in Latvian renders the English text, never the raw key. _(Tested, for a missing key and for an empty one. A second test walks every English key in Latvian and fails on a raw key.)_
- [x] Ingredient counts of 0, 1, 2, 10 and 21 each render the grammatically correct Latvian form, asserted in a test. _(Asserted on servings, the one count the app shows today: porciju, porcija, porcijas, porciju, porcija.)_
- [x] With `unitSystem` imperial, the converter renders an amount stored as `500 g` in pounds or ounces, and one stored as `500 ml` in cups or fluid ounces, asserted in a test until 0007 puts an ingredient on screen. _(Tested: about 1.1 lb, about 2 cups.)_
- [x] No display path converts a volume unit into a mass unit or the reverse, asserted by a test over every pair in the enum. _(Tested over every unit, both systems and five amounts: the dimension never changes and the amount never rounds to zero.)_
- [x] The converter renders `temperatureCelsius` 180 as 356°F for an imperial user, and a body text mentioning 180°C is never passed through it, asserted in a test until 0008 puts a step on screen. _(Tested. The converter takes a number only, so prose cannot reach it.)_
- [ ] Setting `locale` to `null` returns the app to following the device, verified by changing the device language and seeing the app follow. _(The resolution order is tested and the Device row restores null. **Not verified** by changing the simulator's language.)_
- [ ] A device set to Latvian with `locale` null shows Latvian, not English. _(Tested at the resolver. **Not verified** on a device set to Latvian.)_
- [ ] A device set to a language the app does not ship, with `locale` null, shows English. _(Tested at the resolver. **Not verified** on a device.)_
- [ ] An explicit choice survives a device language change: a user who picked English on a Latvian device is still in English afterwards. _(Tested at the resolver. **Not verified** on a device.)_
- [x] `PATCH /api/me` with an unsupported locale returns 400 with `VALIDATION_FAILED`. _(Tested, and `fields` names `locale`.)_
- [ ] Every screen renders without clipping or overlap in Latvian, which is materially longer than English in several labels. _(Settings and the list seen in Latvian on the simulator. **Not verified** on every screen.)_
- [x] A search for `left:`, `right:`, `marginLeft` and `paddingRight` in `apps/mobile/src` returns no matches. _(The only `left` and `right` are safe-area edge names, which are the platform's API rather than layout.)_
- _Manual follow-up, not a gate:_ A VoiceOver or TalkBack walkthrough of the settings screen announces each picker, its current value, and which option is selected, in Latvian as well as English.

## Decided

**The Latvian is AI-drafted, and the project owner corrects it.** Every key ships translated, so the
whole app switches on day one and the fallback path is exercised by a test rather than by users. The
draft will read wrong in places a native speaker notices first; those are fixed in the JSON files as
they are found, which is the only translation tooling this project has.

**Imperial volumes round to a common fraction, or fall back to fluid ounces.** `250 ml` is `1 cup` and
`60 ml` is `1/4 cup`. Where no quarter, third or half of a cup, or a whole spoon, lands within a few
percent, the amount shows in fluid ounces instead, because `3/4 cup minus a teaspoon` is not something
anyone says. Every converted value is marked approximate either way.

**Units ship as a module, screens follow.** Nothing shows an ingredient or a step yet, so the
converter and the unit system setting land here with tests, and 0007 and 0008 put them on screen.
