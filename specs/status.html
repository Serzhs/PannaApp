Requirements, as written in the spec

Goal

A developer can clone the repo, run three commands, and have a linted, typechecked API running against a migrated database, with the Expo app booting on a simulator.

Out of scope

  • Authentication. 0003 owns every auth endpoint and the sign-in screen. This spec creates the users, identities and refresh_tokens tables and writes nothing to them.
  • The design system. 0002 owns tokens and components. The placeholder screen here uses plain React Native styles and is replaced.

  • Any real screen. One placeholder proves the app boots.
  • Deployment, CI, EAS Build, OTA updates.
  • Dark mode. 0002 defines the theme structure that would carry it.

    • Data model

    Create every table listed in CLAUDE.md in the initial migration: users, identities, refreshtokens, recipes, ingredients, equipment, steps, stepingredients, stepequipment, cooks, cooknotes. Later specs add endpoints on top of them and never alter a table that already holds data.

    Also created here: the unit, unitsystem, authprovider, recipestatus Postgres enums, the pgtrgm extension for searching recipe titles, and the citext extension so email uniqueness is case insensitive.

    steps.parentStepId is a nullable self-reference, which is how a step records that it happens during another one. The schema can express the foreign key and nothing else: that a parent belongs to the same recipe, and that nesting never goes more than one level deep, are enforced in application code from 0008 onward.

    docker-compose.yml runs one service, database, on Postgres 16 and port 5433 to avoid clashing with a local install. Credentials come from .env, and .env.example is committed.

    packages/shared holds the contract and the error code const object. A controller's return type is derived from the contract and the mobile client parses against the same schema, so neither side can drift. The mobile client parses each response against its schema before handing it to the caller, so a mismatch surfaces at the boundary rather than as a strange bug three screens later.

    This spec defines one endpoint, so that "it works" is something that can be checked rather than assumed.

    GET /api/health

    Unauthenticated. 200: { status: 'ok', database: 'ok' }. It runs a trivial query, so a database that is unreachable produces a failure here rather than on the first real request.

    Error codes introduced: VALIDATIONFAILED, RATELIMITED.

    UI

    The Expo app boots to a single placeholder screen. It uses plain React Native styles, because 0002 has not happened yet, and it is deleted once real screens exist.

    Error boundary. The app is wrapped in an error boundary, and so is each route group. A render error shows a screen with a way to recover, never a blank app.

    Query wiring. The TanStack Query client is connected to React Native's AppState and to the network state, so it knows when the app is backgrounded and when the phone loses its connection. Without this the offline behaviour in CLAUDE.md does not work, and the failure is silent.

    Requirements, as written in the spec

    Goal

    A user signs in with Google or Apple in one tap, and stays signed in after restarting the app.

    Out of scope

  • Passwords of any kind. There is a development-only sign-in, described in its own section below, and it is deliberately not a password: it mints a session for a user that is already in the seed, and it cannot create one.
  • Facebook, and any third provider. Google and Apple cover almost everyone, and adding another later is a small change.
  • Linking or unlinking providers from a settings screen. Automatic linking is described below; doing it by hand is a later spec.
  • Account deletion, profile editing, avatars.
  • Choosing a language or unit system. 0006 owns that; this spec follows the device locale.
  • Any recipe screen. The signed-in destination is a placeholder.

    • Data model

    No new tables. users, identities and refresh_tokens exist from 0001.

    Account linking. A sign-in is matched to an existing user by (provider, subject) first, which is the only stable key. If there is no match and the provider says the email is verified, the identity is attached to the user holding that email, or a new user is created with it. If there is no match and no verified email, the sign-in is refused with AUTHPROVIDERTOKEN_INVALID.

    Linking on an unverified email would be account takeover: anyone who can get a provider to assert an address they do not own would inherit the account behind it. Creating a separate account instead is not possible either, because users.email is unique and the address may already be taken. Google and Apple both verify addresses, so in practice this path is not reached; it exists so that it fails closed if it ever is.

    A name may be blank. Google puts one in its token. Apple hands one over only if the person agrees, and only the first time. When neither supplies one, displayName is stored empty, until 0017 makes it editable.

    Apple's private relay. Apple lets people hide their real address, giving a unique relay address per app instead. It will never match an existing user, so someone who signs in with Apple privately and later with Google gets two accounts, and there is no way for the app to know they are the same person. That is a limitation of the choice, not a bug to fix here.

    Apple sends a name once. The display name arrives only on the very first authorisation, from the client rather than from the token, and never again. If it is not captured then it is gone, so the first sign-in stores it and later ones leave it alone.

    API contract

    Through the contract in packages/shared. Error codes this spec introduces, alongside VALIDATIONFAILED and RATELIMITED from 0001:

    AUTHPROVIDERTOKENINVALID, AUTHTOKENINVALID, AUTHTOKENEXPIRED, AUTHTOKEN_REVOKED.

    There is no code for "this email already exists", because there is no path where a user asserts an email.

    POST /api/auth/session

    Body: { provider: 'google' | 'apple', idToken, nonce, displayName? }

    200: { user: { id, email, displayName }, accessToken, refreshToken }, for both a new account and an existing one. The response does not say which, because the client does not need to know and the difference is not the client's to act on.

    401 with AUTHPROVIDERTOKEN_INVALID if the token fails any check.

    429 when throttled per IP.

    Verification, in full, per the Security section of CLAUDE.md: signature against the provider's published keys, issuer, audience matching our own client id, expiry, issued-at, and nonce matching the value the client generated for this attempt. email is used only when the provider marks it verified. An access token is never accepted in place of an ID token.

    displayName is accepted only when creating a user, is treated as untrusted text, and is ignored on every later sign-in.

    POST /api/auth/refresh

    Body: { refreshToken }

    200: { accessToken, refreshToken }. The old token is revoked and a new one issued on every use.

    401 with AUTHTOKENINVALID, AUTHTOKENEXPIRED or AUTHTOKENREVOKED.

    Reuse is treated as theft. Presenting a token that has already been used revokes every token in that chain, not only the one presented, and logs it. A stolen refresh token therefore works once, after which both parties are signed out and there is a log line saying so. Revoking only the presented token would leave the thief's fresh token working while the victim's rotation failed, which is the wrong way round. Each refresh token records the token it replaced, so the chain is identifiable.

    POST /api/auth/logout

    Auth required. Revokes the caller's refresh token chain. 204.

    GET /api/me

    Auth required. 200: { id, email, displayName }. 401 without a valid access token.

    Refresh tokens are 256 bits of randomness stored as a SHA-256 hash, never written raw to the database or to logs. Failed verifications, throttle rejections and refresh reuse are logged as authentication events.

    UI

    Expo Router with two route groups, (auth) and (app). Built from 0002's components.

    (auth)/index: the app name, a short line saying what it is for, and two buttons - Continue with Google, Continue with Apple. Nothing else. No email field, no password, no third option.

    In a development build only, a third affordance appears under those two, taking the seeded developer account straight in. It is compiled out of a release bundle, per the Development sign-in section, and is styled as an ordinary Button so nobody mistakes it for a provider.

    The two buttons follow Google's and Apple's own branding rules rather than the app's Button styling, per the Platform behaviour section of CLAUDE.md. Both providers require it, and it is the one place the design system does not win.

    Sign in with Apple appears first on iOS, per Apple's guidance. On Android only Google is offered - the Apple web flow is poor enough not to ship, per the decision recorded under Open questions.

    The client generates a fresh nonce per attempt. It gives the provider the SHA-256 of it and sends the API the nonce itself; the API hashes what it receives and compares it with the token's claim. The token therefore carries only the hash, so holding a captured token is not enough to present it.

    Google runs through its browser sign-in sheet rather than its native SDK, because the free native library cannot pass a nonce. An iOS client has no secret, so the code is exchanged with PKCE alone.

    States: idle, in flight with the pressed button showing a loading state and both disabled, and failed. A cancelled sign-in returns silently to idle, because cancelling is a choice rather than an error. A genuine failure shows a message and lets the user try again or use the other provider. Being offline says so plainly, since sign-in is the one thing that cannot work without a connection.

    (app)/index: placeholder home screen showing the display name and a sign-out button. Replaces 0001's placeholder. Recipes come in 0005.

    The root layout chooses the group based on whether a session exists, showing a splash state while it checks rather than flashing the sign-in screen.

    Tokens are stored in expo-secure-store. The shared client attaches the access token, and on a 401 attempts one refresh, retries once, and on failure clears the session and returns to sign-in. Concurrent 401s trigger exactly one refresh call.

  • Divider — a one-pixel line in borderSubtle.
  • Spinner — a single size and a semantic colour. For a load that replaces known content, prefer Skeleton; a spinner is for an action in flight, not for a screen filling in.
  • Skeleton — a shimmering placeholder in the shape of the content it stands in for, with Skeleton.Text for lines of text and Skeleton.Block for rectangles. Every screen's loading state is built from these, so the layout does not jump when real content arrives. A skeleton whose shape differs from the content it replaces is worse than a spinner, because it promises a layout and then breaks it.
  • EmptyState — title, optional body, optional action slot.
  • ErrorState — message and a retry action. It takes a variant for being offline, because that is a different situation from a failed request and the user can act on only one of them.
  • ConfirmDialog — title, body, confirm and cancel labels, and a destructive flag. It wraps the platform's own alert rather than drawing a custom modal, per the Platform behaviour section of CLAUDE.md. That gets the right look on both phones, correct focus handling and full screen reader support without building any of it, and it is why this component has no styles file.

    • UI

    The design gallery only. Each component gets a section in the /design gallery 0002 set up, showing every variant and state, per the Design system section of CLAUDE.md.

    Skeleton gets one further gallery entry that places a skeleton next to the content it stands in for, so the two can be compared directly. That comparison is the only reliable way to catch the height mismatch that makes a screen jump, and it is not something a test can judge.

    Requirements, as written in the spec

    Goal

    A logged-in user can create, view, edit and delete their own recipes, as metadata only.

    Out of scope

  • Ingredients, steps and the step_ingredients link. The tables exist from 0001 and stay empty.
  • Sharing. shareToken stays null and GET /api/shared/:shareToken is not implemented.
  • Images. coverImageKey stays null and is never written or returned.
  • Search, filtering, sorting controls, tags, categories, favourites.
  • Pagination. A user's own list is returned in full.
  • The in-progress section of the home screen. Cooking does not exist until 0011, so there is nothing to be part-way through. The list ships as one section here and gains the other above it later.
  • The Cook button on the detail screen. Same reason.
  • Offline editing and any mutation queue. Reads are cached per the Offline section of CLAUDE.md; writes require a connection.
  • Duplicating a recipe, importing a recipe, exporting a recipe.
  • Soft delete, trash, undo. Deletion is permanent.
  • Any read access to a recipe by anyone other than its author.

    • Data model

    No new tables and no new columns. The recipes table created in 0001 is used as-is, so this spec adds no migration.

    Fields written by this spec: title, description, servings, totalTimeMinutes, authorId.

    Fields not written by this spec: coverImageKey, shareToken.

    API contract

    All bodies validated by Zod schemas in packages/shared. All routes require a valid access token; without one they return 401 before any authorization check runs.

    Recipe response shape, used by every endpoint below:

    { id, title, description, status, servings, totalTimeMinutes, createdAt, updatedAt }

    authorId, coverImageKey and shareToken are never returned by this spec's endpoints. Sharing state becomes visible to the client in 0016, not here.

    Field rules, shared by create and update:

  • title: string, trimmed, 1 to 120 characters. A title that is empty after trimming is a 400.
  • description: string or null, trimmed, up to 2000 characters.
  • servings: integer, 1 to 100.
  • totalTimeMinutes: integer or null, 1 to 1440.

    • POST /api/recipes

    Body: { title, description?, servings, totalTimeMinutes? }. Omitted optional fields are stored as null. status is not accepted here: every new recipe starts as draft.

    201: recipe response shape.

    400 on validation failure.

    GET /api/recipes

    Returns every recipe owned by the caller, ordered by updatedAt descending, then id descending as a tiebreak so the order is stable when two recipes share a timestamp.

    200: array of recipe response shapes. An author with no recipes gets [], not a 404.

    GET /api/recipes/:recipeId

    200: recipe response shape.

    404 if the recipe does not exist or exists and belongs to another user. The two cases are indistinguishable to the caller, so the endpoint does not reveal which recipe ids are real.

    PATCH /api/recipes/:recipeId

    Body: any subset of { title, description, status, servings, totalTimeMinutes }. status moves a recipe between draft and ready in both directions, because a finished recipe can turn out to need more work. An empty body is a 400. A field present with value null clears it, for the two nullable fields only; title and servings cannot be set to null.

    200: the updated recipe response shape, with updatedAt refreshed.

    404 under the same rule as GET. A rejected update writes nothing.

    DELETE /api/recipes/:recipeId

    204 with an empty body.

    404 under the same rule as GET, including for a recipe that was already deleted.

    Rows in ingredients, steps and step_ingredients are removed by the existing cascades. In this spec those tables are always empty, so the cascade is untested here and is covered by 0007 and 0008.

    Ownership is enforced by a guard, as CLAUDE.md requires, not by checks scattered through the service.

    UI

    Three new routes in the (app) group, plus a change to the existing home screen.

    (app)/index stops being the 0003 placeholder and becomes the recipe list. It keeps the logged-in display name and the logout button, now in the screen header rather than the body.

  • Loading: skeleton rows in the shape of real recipe rows, never a spinner and never a flash of the empty state.
  • Empty: a short line explaining there are no recipes yet, and a primary action that opens the create screen.
  • Error: a message and a retry control that refetches. Being offline is its own state with its own wording, not a generic failure, because the user can act on one and not the other.
  • Populated: one row per recipe showing title, servings and total time when it is set. A recipe in draft carries a chip saying so, and the chip is text rather than only a colour. Tapping a row opens the detail screen. A control in the header opens the create screen.

    • (app)/recipes/new: the first page of the create flow. Creating a recipe is four pages - basics, what you need, the steps, then a review - but only the first exists until 0007 and 0008 add the others, so here it is one page that saves a draft and lands on the recipe. The flow grows into a wizard rather than arriving as one, and this spec builds the shell it grows in.

    A form for the four fields. Submit is disabled while the request is in flight. On success the app navigates to the new recipe's detail screen, and the list reflects it on return without a manual refresh. Field-level errors render against the field; a failure that is not field-specific renders once at form level.

    (app)/recipes/[id]: detail view showing title, description, servings and total time, with actions to edit and to delete. Metadata only. There are no placeholder sections for ingredients or steps, because those are not part of this slice. Loading, error and populated states as above; a 404 renders a "recipe not found" state with a way back to the list, not a crash.

    (app)/recipes/[id]/edit: the whole recipe on one screen, prefilled, submitting a PATCH. Editing never uses the create flow's pages - someone fixing one wrong quantity should not be walked through a wizard to reach it. On success it returns to the detail screen showing the new values.

    Deleting asks for confirmation first. On confirmation the app returns to the list and the deleted recipe is gone from it without a manual refresh.

    All four screens follow the CLAUDE.md mobile conventions: logic in src/features/recipes, routes carrying routing and layout only, all colours and spacing from the typed theme module.

    Requirements, as written in the spec

    Goal

    A user can run the app in English or Latvian, with correct plurals, locale-appropriate formats, and measurements in the system they think in.

    Out of scope

  • Any third language. Adding one must cost a translation file and a line in the locale list, and this spec ships two.
  • Translating recipe content. Titles, ingredient names and step bodies stay in the language their author wrote them in, always. The recipe does not record which language that is, because nothing would read it.
  • Shipping a right-to-left language. The layout discipline that makes one possible is in scope; an actual RTL locale is not.
  • Translation management tooling, string extraction pipelines, or a translator-facing service. Files are edited by hand in the repo.
  • Converting volume to mass. See the limitation below.
  • Localised recipe search or collation. Nothing searches yet.

    • Data model

    No new tables. Two columns created empty by 0001 come into use here:

  • users.locale — a BCP-47 tag, or null for "follow the device".
  • users.unitSystem — metric or imperial, or null for "derive from the locale".

    • Null is a real value in the first two and is not the same as the resolved value. A user on a lv-LV device who explicitly picks English has locale = 'en'; a user who never opened settings has locale = null and follows the device wherever it goes. Storing the resolved value on first launch would silently freeze a preference the user never expressed.

    Resolution order: explicit choice, then device, then English. Null is not English. A Latvian on a Latvian phone who never opened settings gets Latvian; English is the last resort for a device asking for a language the app does not ship. unitSystem resolves the same way and ends at metric.

    API contract

    PATCH /api/me

    Auth required. Body: any subset of { locale, unitSystem, displayName }. Either of the first two may be null, which restores "follow the device".

    200: { id, email, displayName, locale, unitSystem }.

    400 with VALIDATION_FAILED if locale is not in the shipped set or unitSystem is not one of the two enum values.

    GET /api/me gains locale and unitSystem in its response.

    No other endpoint changes. The server does not translate anything, does not read Accept-Language, and does not convert units. It stores the preference; the client does the work.

    Translation

    Files live at apps/mobile/src/i18n/<locale>/<namespace>.json, one namespace per feature, matching the src/features/* folders.

  • Keys are structural, not English: recipes.list.empty.title, never noRecipesYet. A key derived from the English wording has to change when the English changes, which breaks every other language for no reason.
  • English is the source. A key missing from another locale falls back to English rather than rendering the key, because a user seeing recipes.list.empty.title is a worse failure than a user seeing English. An empty string counts as missing too, so a key can be added to English first and the app stays usable until it is translated.
  • Plurals use i18next's plural categories. Latvian resolves to zero, one and other, and its zero form applies to 0, 10, 20 and every number ending in zero, which no hand-written condition gets right by accident.
  • Interpolated values are formatted through Intl, not concatenated.

    • Units

    Conversion happens on display only. Values are stored exactly as the author entered them, in the unit they chose, and unitSystem decides what the reader sees. Storing a canonical value instead would mean the author's own recipe reads back in numbers they did not write.

    Conversion is within a dimension only:

  • Mass to mass, g/kg to oz/lb.
  • Volume to volume, ml/l to tsp/tbsp/cup/floz.
  • temperatureCelsius to Fahrenheit.
  • Count units - piece, pinch, clove, slice - are translated, never converted.

    • Volume to mass is never attempted. Turning 1 cup of an ingredient into grams needs that ingredient's density: a cup of flour and a cup of honey differ by more than a factor of two. Guessing produces a recipe that is confidently, invisibly wrong, which is worse for a cooking app than showing a unit the reader has to think about. So an imperial reader sees cups for a volume and ounces for a mass, and never a mass derived from a volume.

    Converted values are rounded to something a person would say - 250 ml becomes 1 cup, not 1.0567 cups - and a converted value is marked as approximate in the UI so nobody weighs to a precision the conversion does not have. Volumes round to the nearest common cup or spoon fraction when one is close enough, and fall back to fluid ounces when none is, per the decision below.

    Ingredients and steps do not exist on any screen until 0007 and 0008. This spec ships the conversion as a tested module in src/features/units, with the setting that drives it, and those specs put it on screen. The unit criteria below are therefore asserted against the module, not a screen.

    A temperature written into a step's body as prose is not converted, because that would mean rewriting user text. Only temperatureCelsius converts, which is the reason the column exists.

Each picker's "Device" option is the null state and shows what the device currently resolves to, so the choice is legible rather than blank.
