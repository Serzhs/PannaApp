    Requirements, as written in the spec

    Goal

    A user signs in with Google or Apple in one tap, and stays signed in after restarting the app.

    Out of scope

  • Passwords of any kind. There is a development-only sign-in, described in its own section below, and it is deliberately not a password: it mints a session for a user that is already in the seed, and it cannot create one.
  • Facebook, and any third provider. Google and Apple cover almost everyone, and adding another later is a small change.
  • Linking or unlinking providers from a settings screen. Automatic linking is described below; doing it by hand is a later spec.
  • Account deletion, profile editing, avatars.
  • Choosing a language or unit system. 0006 owns that; this spec follows the device locale.
  • Any recipe screen. The signed-in destination is a placeholder.

    • Data model

    No new tables. users, identities and refresh_tokens exist from 0001.

    Account linking. A sign-in is matched to an existing user by (provider, subject) first, which is the only stable key. If there is no match and the provider says the email is verified, the identity is attached to the user holding that email, or a new user is created with it. If there is no match and no verified email, the sign-in is refused with AUTHPROVIDERTOKEN_INVALID.

    Linking on an unverified email would be account takeover: anyone who can get a provider to assert an address they do not own would inherit the account behind it. Creating a separate account instead is not possible either, because users.email is unique and the address may already be taken. Google and Apple both verify addresses, so in practice this path is not reached; it exists so that it fails closed if it ever is.

    A name may be blank. Google puts one in its token. Apple hands one over only if the person agrees, and only the first time. When neither supplies one, displayName is stored empty, until 0018 makes it editable.

    Apple's private relay. Apple lets people hide their real address, giving a unique relay address per app instead. It will never match an existing user, so someone who signs in with Apple privately and later with Google gets two accounts, and there is no way for the app to know they are the same person. That is a limitation of the choice, not a bug to fix here.

    Apple sends a name once. The display name arrives only on the very first authorisation, from the client rather than from the token, and never again. If it is not captured then it is gone, so the first sign-in stores it and later ones leave it alone.

    API contract

    Through the contract in packages/shared. Error codes this spec introduces, alongside VALIDATIONFAILED and RATELIMITED from 0001:

    AUTHPROVIDERTOKENINVALID, AUTHTOKENINVALID, AUTHTOKENEXPIRED, AUTHTOKEN_REVOKED.

    There is no code for "this email already exists", because there is no path where a user asserts an email.

    POST /api/auth/session

    Body: { provider: 'google' | 'apple', idToken, nonce, displayName? }

    200: { user: { id, email, displayName }, accessToken, refreshToken }, for both a new account and an existing one. The response does not say which, because the client does not need to know and the difference is not the client's to act on.

    401 with AUTHPROVIDERTOKEN_INVALID if the token fails any check.

    429 when throttled per IP.

    Verification, in full, per the Security section of CLAUDE.md: signature against the provider's published keys, issuer, audience matching our own client id, expiry, issued-at, and nonce matching the value the client generated for this attempt. email is used only when the provider marks it verified. An access token is never accepted in place of an ID token.

    displayName is accepted only when creating a user, is treated as untrusted text, and is ignored on every later sign-in.

    POST /api/auth/refresh

    Body: { refreshToken }

    200: { accessToken, refreshToken }. The old token is revoked and a new one issued on every use.

    401 with AUTHTOKENINVALID, AUTHTOKENEXPIRED or AUTHTOKENREVOKED.

    Reuse is treated as theft. Presenting a token that has already been used revokes every token in that chain, not only the one presented, and logs it. A stolen refresh token therefore works once, after which both parties are signed out and there is a log line saying so. Revoking only the presented token would leave the thief's fresh token working while the victim's rotation failed, which is the wrong way round. Each refresh token records the token it replaced, so the chain is identifiable.

    POST /api/auth/logout

    Auth required. Revokes the caller's refresh token chain. 204.

    GET /api/me

    Auth required. 200: { id, email, displayName }. 401 without a valid access token.

    Refresh tokens are 256 bits of randomness stored as a SHA-256 hash, never written raw to the database or to logs. Failed verifications, throttle rejections and refresh reuse are logged as authentication events.

    UI

    Expo Router with two route groups, (auth) and (app). Built from 0002's components.

    (auth)/index: the app name, a short line saying what it is for, and two buttons - Continue with Google, Continue with Apple. Nothing else. No email field, no password, no third option.

    In a development build only, a third affordance appears under those two, taking the seeded developer account straight in. It is compiled out of a release bundle, per the Development sign-in section, and is styled as an ordinary Button so nobody mistakes it for a provider.

    The two buttons follow Google's and Apple's own branding rules rather than the app's Button styling, per the Platform behaviour section of CLAUDE.md. Both providers require it, and it is the one place the design system does not win.

    Sign in with Apple appears first on iOS, per Apple's guidance. On Android only Google is offered - the Apple web flow is poor enough not to ship, per the decision recorded under Open questions.

    The client generates a fresh nonce per attempt. It gives the provider the SHA-256 of it and sends the API the nonce itself; the API hashes what it receives and compares it with the token's claim. The token therefore carries only the hash, so holding a captured token is not enough to present it.

    Google runs through its browser sign-in sheet rather than its native SDK, because the free native library cannot pass a nonce. An iOS client has no secret, so the code is exchanged with PKCE alone.

    States: idle, in flight with the pressed button showing a loading state and both disabled, and failed. A cancelled sign-in returns silently to idle, because cancelling is a choice rather than an error. A genuine failure shows a message and lets the user try again or use the other provider. Being offline says so plainly, since sign-in is the one thing that cannot work without a connection.

    (app)/index: placeholder home screen showing the display name and a sign-out button. Replaces 0001's placeholder. Recipes come in 0005.

    The root layout chooses the group based on whether a session exists, showing a splash state while it checks rather than flashing the sign-in screen.

    Tokens are stored in expo-secure-store. The shared client attaches the access token, and on a 401 attempts one refresh, retries once, and on failure clears the session and returns to sign-in. Concurrent 401s trigger exactly one refresh call.

    • Data model

    No new tables. Two columns created empty by 0001 come into use here:

  • users.locale — a BCP-47 tag, or null for "follow the device".

    PATCH /api/me

    Translation

    Files live at apps/mobile/src/i18n/<locale>/<namespace>.json, one namespace per feature, matching the src/features/* folders.

  • Keys are structural, not English: recipes.list.empty.title, never noRecipesYet. A key derived from the English wording has to change when the English changes, which breaks every other language for no reason.
  • English is the source. A key missing from another locale falls back to English rather than rendering the key, because a user seeing recipes.list.empty.title is a worse failure than a user seeing English. An empty string counts as missing too, so a key can be added to English first and the app stays usable until it is translated.
  • Plurals use i18next's plural categories. Latvian resolves to zero, one and other, and its zero form applies to 0, 10, 20 and every number ending in zero, which no hand-written condition gets right by accident.
  • Interpolated values are formatted through Intl, not concatenated.

    • Units

    Conversion happens on display only. Values are stored exactly as the author entered them, in the unit they chose, and unitSystem decides what the reader sees. Storing a canonical value instead would mean the author's own recipe reads back in numbers they did not write.

    Conversion is within a dimension only:

  • Mass to mass, g/kg to oz/lb.
  • Volume to volume, ml/l to tsp/tbsp/cup/floz.
  • temperatureCelsius to Fahrenheit.
  • Count units - piece, pinch, clove, slice - are translated, never converted.

    • Volume to mass is never attempted. Turning 1 cup of an ingredient into grams needs that ingredient's density: a cup of flour and a cup of honey differ by more than a factor of two. Guessing produces a recipe that is confidently, invisibly wrong, which is worse for a cooking app than showing a unit the reader has to think about. So an imperial reader sees cups for a volume and ounces for a mass, and never a mass derived from a volume.

    Converted values are rounded to something a person would say - 250 ml becomes 1 cup, not 1.0567 cups - and a converted value is marked as approximate in the UI so nobody weighs to a precision the conversion does not have. Volumes round to the nearest common cup or spoon fraction when one is close enough, and fall back to fluid ounces when none is, per the decision below.

    Ingredients and steps do not exist on any screen until 0007 and 0008. This spec ships the conversion as a tested module in src/features/units, with the setting that drives it, and those specs put it on screen. The unit criteria below are therefore asserted against the module, not a screen.

    A temperature written into a step's body as prose is not converted, because that would mean rewriting user text. Only temperatureCelsius converts, which is the reason the column exists.

  • optional: boolean, default false.

    Goal

    An author writes a recipe's steps in order, nesting under a step whatever can be done during it, and a reader sees the steps numbered with the nested ones marked as things to do meanwhile.

    Out of scope

  • Linking a step to the ingredients and equipment it uses. That is 0010, and it is why steps keep their ids across an edit.
  • Cooking mode, timers, ticking steps off, keeping the screen awake. 0012.
  • A picture of what a step should look like. imageKey stays null; 0011.
  • Cook's notes on a step. steps.note is the author's tip and part of the recipe; the cook's own dated notes are 0015 and a different table.
  • More than one level of nesting. A nested step cannot itself have nested steps, per the Data model section of CLAUDE.md, and the request shape below makes a second level impossible to express rather than merely refused.
  • Converting a temperature written into a step's text. Only the temperatureCelsius column is converted, per 0006; prose is the author's and is never rewritten.
  • Moving a step by dragging it into or out of a parent. A step moves within its level by drag or buttons; changing its level is a button, because a drag that can also re-parent is two gestures pretending to be one.
  • Reading steps aloud, voice input, or any audio. Ruled out for the whole app in CLAUDE.md.
  • Scaling durations or amounts by servings.
  • The review page of the create flow and marking a recipe ready. That is the next spec, a short one, before step links.

    • Data model

    No new tables and no new columns. steps from 0001 is used as it is, so there is no migration.

    A step with a null parentStepId is a main step, done in sequence. A step with a parentStepId happens during that step. The author decides this by nesting, and nothing else: two steps that merely have nothing to do with each other are not parallel.

    position is a zero-based integer, unique among siblings: among the main steps, and among the children of one parent. Reordering rewrites every position in one transaction. Nothing relies on insertion order.

    body is the instruction, short enough to read at a glance with a knife in the other hand. note is anything extra worth knowing while doing it. They stay apart so the instruction stays short.

    durationSeconds is how long the step takes, or null when it is not timed. temperatureCelsius is the oven or pan temperature, or null; it is stored in Celsius whatever the author's unit system, and converted only for reading.

    Total time is derived from here on. recipes.totalTimeMinutes becomes the sum of the main steps' durations, rounded up to a whole minute, and null when no main step is timed. Nested steps happen inside a main step's time and add nothing, which is the whole point of nesting them. The column stays, recomputed on every write to the steps, so the list screen can show it without a join. It leaves the create and edit forms, as 0005 decided, and a body that still sends it is refused.

    Deleting a main step promotes its nested steps to main steps at its position, in order. It does not delete them. Losing four steps because one was removed is the kind of thing people do not forgive.

    API contract

    All routes require a valid access token and answer 401 without one. Ownership goes through the guard 0005 added: a recipe that does not exist and one that belongs to someone else both answer 404 with RECIPENOTFOUND, with identical bodies.

    Field rules for a step:

  • body: string, trimmed, 1 to 2000 characters.
  • note: string or null, trimmed, up to 500 characters.
  • durationSeconds: integer or null, 1 to 86400.
  • temperatureCelsius: integer or null, -50 to 500.

    • A recipe holds at most 60 main steps, and a main step at most 20 nested steps.

    Step shape, in every response that carries it, nested one level so the structure is visible rather than reconstructed from ids:

    ```

    { id, position, body, note, durationSeconds, temperatureCelsius,

    children: [ { id, position, body, note, durationSeconds, temperatureCelsius } ] }

    ```

    Main steps are ordered by position, and so are the children within each one.

    GET /api/recipes/:recipeId gains steps, an array of main steps in that shape, [] for a recipe with none. The list endpoint does not carry steps.

    PATCH /api/recipes/:recipeId accepts a further optional field, steps, the complete list in the order it should have, in the same nested shape without position. It is written in the same transaction as the metadata and the lists from 0007, and the rules are the ones 0007 established:

  • A row with an id that belongs to this recipe is updated in place and keeps its id, wherever it now sits: a step may move to another position, under another parent, or from nested to main and back, and stays the same step. This is what keeps 0010's links alive through an edit.
  • A row with no id is inserted.
  • A row absent from the body is deleted. A main step absent from the body whose children are present elsewhere in the body keeps those children, which is how the promotion rule is expressed: the client lists the orphaned steps as main steps, and the server never deletes a row the body still names.
  • position is not sent; it is the index in its array. A child's parentStepId is the step it is listed under.
  • A child carrying a children field is a 400: the shape has no second level.

    • After the write, totalTimeMinutes is recomputed from the main steps and returned. totalTimeMinutes is no longer accepted in the POST /api/recipes or PATCH body: sending it is an unknown field, a 400.

    400 with VALIDATION_FAILED and a fields object, and nothing written, when any field breaks its rule, an id appears twice, an id is not one of this recipe's steps, or a cap is passed. A fields key names the step, as in steps.2.body or steps.2.children.1.durationSeconds.

    Error codes this spec can return: AUTHTOKENINVALID, AUTHTOKENEXPIRED, RECIPENOTFOUND, VALIDATION_FAILED.

    UI

The total time in the header is now the derived one.

    To a screen reader a step is one element: its number, body, timing and note read together, and a nested step announces that it belongs to its parent.

    Edit screen, (app)/recipes/[id]/edit. Below the lists from 0007, the steps. A main step is a card with body, note, duration and temperature, and under it its nested steps as smaller cards.
